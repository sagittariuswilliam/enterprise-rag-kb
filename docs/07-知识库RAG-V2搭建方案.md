# 企业知识库 RAG V2 搭建方案

**版本：** V1.0（讨论稿，待拍板）
**日期：** 2026-10-13
**定位：** 本系统 V1 演进（不是新项目）——复用现有接入 4 层框架 + 检索链，新增身份/权限/打包三块
**核心原则：权限跟着 chunk 走，在检索那一刻生效，而不是检索完再遮挡。**

---

## 0. 现状 vs 改后对比（先看这张表）

| 环节 | V1（问答版） | 知识库 V2 |
|---|---|---|
| 使用者 | 只有你一个人，无登录 | 全体员工，钉钉扫码登录 |
| 用户身份 | 无 | 从钉钉通讯录同步（ userid / 部门 / 主管标志） |
| 上传 | 你手动传，无归属 | 员工自助上传，强制选可见级别，部门归属自动带出 |
| 文档类型 | 教材/问答文本 | 文档、表格、PDF、扫描件、图片（复用 V1 接入层） |
| 检索 | 全库召回 | 全库召回 + **本人权限过滤**（Qdrant payload filter） |
| 引用 | 显示来源 | 只显示有权查看的来源，无权文档连标题都不出现 |
| 调岗/离职 | 不涉及 | 钉钉事件实时同步，权限秒级生效 |
| 导出 | 无 | 招投标打包：AI 组清单 → 人工确认 → 受控交付（链接+水印/钉钉通知） |
| 审计 | 无 | 全量日志：谁查过什么、看过哪篇、导出过什么 |

## 1. 功能设计

### 1.1 可见性分级（4 档，不再多）

| 级别 | 谁能看 | 典型内容 | 变更管控 |
|---|---|---|---|
| L1 私密 | 仅上传者本人 | 个人笔记、草稿 | 自由升降 |
| L2 部门 | 本部门（含子部门可选）全员 | 内部 SOP、流程说明 | 默认级别 |
| L3 公司 | 全员 | 制度、产品资料、培训材料 | 升为 L3 需部门负责人确认 |
| L4 指定 | 手工勾选部门/人 | 合同档案、招投标底价、财务报表 | 必须指定审批人，审批通过才生效 |

规则（写死在产品逻辑里）：
- **默认 L2**，上传不选就是部门级——宁可少可见，不可误公开。
- **L4 双人规则**：上传者选的可见范围，需另一名有权限的人（部门负责人或知识库管理员）确认后才发布。
- **文档级标定，chunk 级继承**：人只选一次，切块后 ACL 写入每个 chunk。禁止 chunk 级单独调权限（管理成本失控）。
- 可见级别可以后续修改，改级别 = 只更新向量库 payload（见 §3.5），**不需要重新解析和重新向量化**，秒级生效。

### 1.2 角色与权限矩阵

| 能力 | 普通员工 | 部门知识管理员（每部门 1-2 人） | 知识库管理员（IT/总经办） |
|---|---|---|---|
| 检索问答（权限内） | ✅ | ✅ | ✅ |
| 上传文档 | ✅（默认归本部门） | ✅ | ✅ |
| 审批本部门 L4 文档 | ❌ | ✅ | ✅ |
| 修改文档可见级别 | 仅自己上传的 | 仅本部门的 | 全部 |
| 批量导入存量档案 | ❌ | ✅（走批次默认级别） | ✅ |
| 招投标打包导出 | ✅（结果仅权限内） | ✅ | ✅ |
| 看审计日志 | ❌ | 本部门 | 全部 |
| 用户/部门管理 | ❌ | ❌ | 自动同步，只读 |

### 1.3 上传流程（员工视角）

1. 钉钉扫码登录 → 「上传文档」页
2. 拖入文件（支持 pdf/docx/xlsx/pptx/图片，批量可拖整个文件夹）
3. 选择可见级别（默认 L2，页面把 4 档含义直接标在旁边）
4. L4 → 勾选可见部门/人员 + 选审批人 → 提交后进「待审批」
5. 系统异步解析（状态机：排队 → 解析中 → 待校对(OCR低置信时) → 已入库），完成钉钉工作通知推给上传者
6. 解析完可预览切块效果，不满意可撤回重传

存量档案批量导入（部门管理员）：一次拖一批，给整批设默认级别 + 默认归属部门，逐文件仍走同一状态机与门禁；合同扫描件识别不到文字层的自动标「待校对」，不强行进库。

### 1.4 检索问答（员工视角）

与 V1 的体验一致（聊天框提问），差别：
- 顶部/引用处只显示**我有权看**的来源（标题+页码），点引用可打开原文预览（带水印：工号+时间）
- 回答口径加一句兜底：「未找到相关内容」≠「没有相关内容」——答案尾部固定标注检索范围（如：已检索 制度类/产品类 共 12 篇，另有权限受限文档未纳入本次回答）。**这句话很重要**：否则员工会以为知识库里没有，实际是有但他看不见。

### 1.5 招投标打包（员工视角）

1. 员工在检索页描述投标需求（"XX项目，市政环卫设备，需要资质、业绩、报价模板相关内容"）
2. AI 拆解成多个查询 → 权限内召回 → **按文档聚合去重** → 生成材料清单（标题/部门/级别/命中理由）
3. **人工确认闸门**：员工勾选增删，确认后才生成包。AI 只组清单，不直接发货——漏一份废标、多一份泄密，必须有人签字这一步
4. 交付形态（默认第一种）：
   - **受控链接包**：生成一个有效期（默认 7 天）的在线包页面，逐次查看实时校验权限+水印；员工把链接发给自己或投标小组
   - **钉钉通知发送**（🔄 2026-10-21 拍板：替代原"企业邮箱 SMTP"方案）：系统通过已上线的钉钉机器人单聊，把清单摘要+受控链接直达发起人/投标小组。理由：受控链接每次打开都要求钉钉登录身份，外部人员本就打不开——收件人只可能是内部员工，而钉钉链路已在 L4 审批通知实测送达（notify_ok 有记录），邮件反而要等 IT 开 SMTP 账号。留痕主体在审计日志，与收件通道无关。详见 16 号文档
   - 离线 PDF 打包下载：带水印+审计记录，作为可选项而非默认
5. 打包动作全部记审计日志。

### 1.6 典型使用场景走查（帮助功能验收）

- **销售查产品政策**：钉钉登录→问"巡检车质保政策"→答案带引用[3]，点开是产品手册第 12 页，水印是自己工号。
- **员工调岗**（销售→行政）：钉钉 HR 改了部门，10 分钟内知识库同步（Stream 事件实时，兜底每晚全量对账）。该员工再检索，销售话术库立即召不回，行政制度立即能召回。无需任何人手动改权限。
- **离职**：收到 `user_leave_org` 事件 → active=false → 登录入口即断，已发出的受控链接包同步失效。
- **投标经理打包**：描述需求→AI 给 23 篇清单→他删 4 篇不相关的、手动搜加 2 篇→确认→钉钉收到清单摘要+链接。审计日志记下这次导出的完整文档集合。

## 2. 技术架构总览

```
                    ┌─ 钉钉开放平台（企业内部应用）
                    │   扫码登录 / 通讯录API / Stream事件
                    ▼
浏览器 ── nginx ── FastAPI(本系统)
                    │  ├─ auth/   新增: 钉钉登录+会话(JWT)
                    │  ├─ sync/   新增: 通讯录同步(Stream+全量对账)
                    │  ├─ acl/    新增: 权限模型+过滤构造(唯一出口)
                    │  ├─ api/    改造: upload/chat/history + 新增admin/packages/audit
                    │  └─ services/ 复用: router/parser/ocr/chunker/gate/embedder/reranker/retriever/llm
                    ▼
        SQLite(业务库: users/depts/docs/acl/audit/packages)
        Qdrant(kb_chunks 单 collection, ACL 在 payload)
        DashScope(qwen3.7-embedding / rerank / qwen3.8-flash, 沿用现有配置)
```

改动策略与 V1 接入层改造同原则：**新增旁路模块，旧 services 除 retriever 加 filter 参数外不动**，零回归。

## 3. 关键技术设计

### 3.1 身份认证：钉钉扫码登录

- 钉钉开发者后台建**企业内部应用**，拿到 AppKey/AppSecret
- Web 端用钉钉统一登录（扫码/免登跳转），后端拿 `authUserInfo` 换 `userid`
- userid 对到本地 `users` 表（同步已预灌），发**短期 JWT**（2h）给前端会话
- 关键点：**JWT 里只放 userid，不放部门**——部门每次查询实时从库里取，保证调岗即时生效（若把部门塞进 JWT，调岗后最长要等 token 过期才生效，这是设计事故）

### 3.2 组织同步：钉钉通讯录（已核实官方能力）

| 需求 | 官方接口 | 说明 |
|---|---|---|
| 全量拉部门 | `/topapi/v2/department/listsub` | 递归建树 |
| 全量拉部门成员 | `/topapi/v2/user/list` | 返回 userid/name/**dept_id_list(数组,一人多部门)**/leader/boss/active |
| 变更事件实时推送 | 事件订阅 **Stream 模式**（官方 Python SDK `dingtalk-stream`） | `user_add_org / user_modify_org / user_leave_org / dept_*`；WebSocket 出站长连接，**无需公网回调地址、无需自建域名**，本机即可接 |
| 兜底对账 | 每晚定时全量拉一遍 diff | 防事件丢失，官方文档推荐的组合模式 |

- 一人多部门：`dept_id_list` 是数组，权限判断用 any 语义（任一所属部门命中即有该部门可见内容）。
- 调岗 = `user_modify_org` 里 dept_id_list 变化 → 更新 users.dept_ids → 下一次检索自然生效，**没有任何"逐个文档改权限"的动作**。这是"权限跟属性走"模型的红利。
- OA 数据源问题：公司有自建 OA，但组织架构建议**以钉钉为唯一真源**（OA 若有独立编制，先人工对齐到钉钉），避免双源同步打架。见 §5 待拍板 #1。

### 3.3 权限模型（数据层）

```sql
-- 同步表（钉钉为源，本库只读镜像）
users(userid PK, name, dept_ids JSON, leader BOOL, active BOOL, synced_at)
depts(dept_id PK, name, parent_id)

-- 业务表
docs(doc_id PK, title, owner_userid, dept_id, level TEXT CHECK(level IN('L1','L2','L3','L4')),
     status TEXT,  -- 排队/解析中/待校对/已入库/待审批/已拒绝/已撤回
     sha256, mime, page_count, created_at, updated_at)
doc_acl(doc_id FK, scope TEXT, target_id TEXT)
     -- L4 的附加可见范围: ('dept','23') / ('user','zhangsan')
approvals(doc_id FK, approver_userid, result, ts)
audit_log(id, userid, action TEXT,        -- query/view_doc/download/export_package/change_level
          detail JSON, ip, ts)             -- 保留 180 天
packages(package_id PK, creator_userid, title, doc_ids JSON, token, expires_at, created_at)
package_views(package_id, userid, ts)     -- 受控链接每次访问都记
```

### 3.4 检索侧强制（全系统唯一出口）

所有召回路径（问答、打包、预览、引用回显）必须经过同一个函数，禁止任何模块绕开自拼查询：

```python
def build_acl_filter(user) -> qdrant_client.models.Filter:
    my_depts = user.dept_ids  # 实时从库取
    return Filter(must=[..., should=[
        FieldCondition(key="level", match=MatchAny(any=["L3"])),
        FieldCondition(key="level", match=MatchValue("L2")),
        FieldCondition(key="dept_id", match=MatchAny(any=my_depts)),
        FieldCondition(key="owner_userid", match=MatchValue(user.userid)),
        FieldCondition(key="extra_acl", match=MatchAny(any=[user.userid, *my_depts])),
    ]])
```

对应 Qdrant collection `kb_chunks` payload 设计：

```json
{ "doc_id": "...", "chunk_id": 12, "text": "...", "source": "文件名", "page": 7,
  "level": "L2", "dept_id": "23", "owner_userid": "zhangsan", "extra_acl": [] }
```

- `level`/`dept_id`/`doc_id` 建 payload index（否则 filter 扫全库变慢）。
- V1 现有 `rag_docs` collection 只有 1 个测试 chunk，**无迁移负担**：直接新建 `kb_chunks`，老库 drop。
- 沿用 V1 教训：upsert 分批（<200 chunk/批）、失败透传底层异常、哈希去重——这些逻辑直接复用。

### 3.5 改级别 = 改 payload，不改向量

```python
qdrant.set_payload(collection="kb_chunks",
                   points=Filter(...doc_id...),
                   payload={"level": new_level, ...}, ...)
```

一条 `doc_id` 过滤的 set_payload 完成，秒级、零重算成本。这是"chunk 继承文档 ACL"设计的第二个红利。

### 3.6 LLM-Wiki 如何配合（二期，条件触发）

- 架构 = 决策框架 Pattern A：原文 chunk 主索引 + wiki 精化索引**双索引并存**。
- **硬约束（权限场景特有）**：wiki 条目由 LLM 改写生成，改写必须**逐文档在其权限边界内做**，wiki chunk 携带与原文档完全相同的 ACL payload；跨部门文档合并改写禁止——否则一篇 L4 内容会被"洗"成看似普适的公共条目，权限体系从内部被打穿。
- 触发条件：纯 RAG 上线后真实用户抱怨"答案噪音大/引用碎"再启动，按文档热度排队改写（只改写高频命中的那 20%），不要预建。

### 3.7 打包/通知的技术路径

- 组包 = 检索变体：LLM 拆解查询 → ACL filter 召回 → 按 doc_id 聚合 → 清单落 `packages` 表 → 生成随机 token 的受控链接页（查看时再次过 `build_acl_filter`，**不是发出去就失控**）
- 通知只发「清单摘要 + 受控链接」，**默认不附带原文附件**（附件 = 内容离开权限体系；离线包为显式可选项且记审计）
- 发送通道（🔄 2026-10-21 拍板改钉钉，原企业邮箱 SMTP 方案作废）：复用已上线的钉钉机器人单聊链路（同 L4 审批通知）。接口层仍做成可配置 provider：钉钉为默认实现，SMTP 留桩不实现——将来出现真·外部收件需求再启用。

## 6. 风险与明确不做的

- **扫描件吞吐**：合同档案大量是扫描件，OCR 走 qwen-vl-ocr（成本已验证不是瓶颈，618 页约 ¥1-3），瓶颈是**排队时间**——批量导入做异步队列+状态机，不承诺"传完秒入库"，向使用者明确预期。
- **PII**：合同含个人身份信息，本期不做脱敏（检索者本来就有权限看原文才召回）；若未来出现"低权限员工批量浏览合同"需求，再引入字段遮蔽层。
- **明确不做**：chunk 级独立权限、按部门分 collection、权限进 JWT、AI 自动判密级、通知直发原文附件。这五件事都输掉了同类项目的权限模型，写下来防止以后手痒。
