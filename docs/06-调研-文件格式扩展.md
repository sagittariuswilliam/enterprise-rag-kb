# 06-调研：知识库支持文件格式扩展（2026-10-16）

## 背景与需求

P1 完成后、正式文件批量上传前，用户提出：**目前只支持 PDF / DOCX / TXT / MD，正式资料里有大量表格和图片，格式远不止这些**。（截图实证：共享文档机目录含 WPS PDF、xlsx 类表格，按年度组织的财务数据文件夹。）

当前支持（实测代码）：
- `app/api/upload.py` ALLOWED_EXTS = {.pdf, .docx, .txt, .md, .markdown}
- `app/services/parser.py` SUPPORTED_EXTENSIONS 同上；PDF 走 pypdf（空文字层自动转 OCR 路由），DOCX 走 python-docx（含表格 + 内嵌图片 OCR，D6）
- OCR：DashScope `qwen3.5-ocr`（fallback qwen-vl-ocr-2025-11-20），已有逐页渲染 JPEG→识别的成熟管道（ocr_parser.py）

环境实测（本机 Alinux3）：
- venv 已装 pillow 12.3.0；**未装** pandas/openpyxl/xlrd/python-pptx/markitdown
- LibreOffice 未安装，但 yum 源有 **libreoffice 7.1.8.1**（alinux3-updates 官方包）
- 磁盘剩 21G，内存可用 3.9G —— 装 LibreOffice（约 400-500MB）没问题

## 候选方案调研

### A. MarkItDown（微软开源，一键万物转 Markdown）
- 来源：https://github.com/microsoft/markitdown （README 官方原文）
- 支持：PDF/PPT/Word/Excel/图片(含OCR)/音频/HTML/CSV/JSON/ZIP 等
- 官方自述定位："output meant for text analysis tools, not high-fidelity human consumption"
- PyPI 最新 0.1.8，需 Python 3.10+（我们 3.11 ✅）
- ⚠️ 官方 SECURITY 章节明确警告：**不要把不可信输入直接喂 convert()**，内部会做文件路径/URI 解析，需自己清洗输入
- 评估结论：**不作为核心解析器**。理由：① 我们 PDF 链路（pypdf + qwen OCR + 状态机）已打磨且成本验证过，MarkItDown 的 PDF 质量反而不如；② 安全面扩大（员工上传文件=不可信输入）；③ 它的表格处理（pandas 路线）与 B 方案重叠。**可选装作 [xlsx][pptx] extra 做兜底对比**，不引入为依赖。

### B. 分格式专用库（推荐主路线）
| 格式 | 库 | 依据 |
|---|---|---|
| .xlsx/.xlsm | openpyxl(读) + pandas | 官方成熟；配合"每 sheet → markdown 表"转换 |
| .xls(老版) | xlrd 2.0.2 | 官方声明 2.x 仅支持 .xls，正合适 |
| .csv | pandas（编码探测 utf-8/gbk，中文表常见 gbk） | WPS 导出 csv 多为 gbk |
| .pptx | python-pptx 1.0.2 | 逐页取文本框+表格，转 markdown 分节 |
| .jpg/.png/.bmp/.webp | **复用现有 qwen OCR 管道**（Pillow 打开→JPEG 归一→识别） | 已有 ocr_parser，零新依赖 |

### C. 老格式 .doc/.wps：LibreOffice headless 转换
- `yum install libreoffice-headless libreoffice-calc libreoffice-writer`（7.1.8，官方源）
- `soffice --headless --convert-to docx file.doc` 是 Linux 下 .doc 事实标准（腾讯云/CSDN 多篇对比结论一致：纯 python 的 .doc 读取库（olefile 手解/antiword）对中文和表格支持都不稳）
- ⚠️ **.wps（WPS 私有格式）LibreOffice 支持有限** → 政策：拒收 .wps，提示用户另存为 .doc/.docx（公司机器装了 WPS，一步的事）

### D. 表格类文档的切块策略（关键设计，不是解析而是入库）
调研来源：r/RAG 表格切块讨论、llama_index issue #10316、TableChunker 实践文（LinkedIn/kalyanksnlp）、towardsai《RAG Chunking for Tabular Data》。
共识做法：
1. **小表（≤30 行）**：整个 sheet 转 markdown 表（保留表头），作为一个 chunk。
2. **大表**：按行切块，**每块重复表头**（否则 embedding 检索后 LLM 看到的行没有列名，答案质量崩塌）。
3. **每行做"句子化"增强**（可选二期）：`张三 的 25年单位缴费 是 1200元` 式行转句，提升口语化提问命中率。
4. sheet 名 + 文件名拼进 chunk 元数据（source 字段），检索引用能定位到"哪个表"。

## 推荐结论（一条主线）

1. **新增支持清单**：`.xlsx .xls .csv .pptx .doc(经LibreOffice转docx) .jpg .jpeg .png .bmp .webp` + 现有 5 种 = 共 14 种
2. **实现位置**：
   - `app/services/parser.py`：路由表扩 `parse_excel()/parse_pptx()/parse_image()/parse_legacy_doc()`
   - `app/api/upload.py` ALLOWED_EXTS 同步扩；前端 dropzone 文案与 accept 属性同步
   - Excel 切块走 D 策略进 `chunker.py`（表格感知的行切块）
   - `.doc` 转换：subprocess 调 soffice headless，转换失败→标"解析失败"并说明原因（不悄悄丢内容）
   - 图片：直接走现有 OCR 路由（router.py 加 image 分支）
3. **依赖安装**：venv 装 openpyxl/xlrd/pandas/python-pptx；yum 装 libreoffice（headless + writer + calc）
4. **拒收清单**（明确报错提示，不静默失败）：`.wps .et .ofd .rar .zip`（zip 有安全风险且内部文件权限无法逐份设密级）

## 风险与留验

- LibreOffice 7.1 较老（源里只有这个版本）：对 .doc 转换足够，若实际遇到转换烂的案例再议升级/在线转换兜底
- pandas 大文件内存：财务表若几十万行，需 max_rows 熔断（如 5 万行），超限提示拆分上传
- qwen3.5-ocr 单图成本：照片类页数少，成本不是瓶颈（618 页教材 ¥1-3 已验证）
- **待用户答**（影响二期增强）：① Excel 是纯数据表还是夹大段制度文字；② 图片是"文件的照片"还是"图本身就是资料（架构图）"。默认按本文方案走不阻塞。
