# RAG 智能客服 — 整体架构与使用指南

> 版本: v2.2 (P0-P4 权限体系+打包审批上线后) | 更新: 2026-10-21 | 服务端口: 9012
> 本文档描述**当前真实运行状态**，与代码逐文件核对过。
> 权限/密级/打包等业务层设计不在本文展开，见 docs/10（决策版）、docs/16（P4 打包 V1.1）、docs/00 只管接入与检索链路。

---

## 一、这个系统解决什么问题

**目标**：公司内部文档（制度、教材、SOP、扫描版书籍）入库后，员工用自然语言提问，
系统从文档中检索相关片段，由 AI 组织成带**页码引用**的回答。

**核心信念**：RAG 的质量上限由"入库质量"决定，不由模型决定。
垃圾进 → 垃圾出。所以整个架构的重心在**接入层**（把任何格式的文件可靠地变成干净文本），
其次才是检索层和生成层。

---

## 二、整体思路（四条设计公理）

1. **每份文档都能被读取** —— 不管是原生 PDF、Word、表格还是整本扫描件，
   接入层必须有明确的分流路径；识别不了的格式要如实拒绝，绝不假装成功。
2. **失败必须可见** —— OCR 额度耗尽、文件解析为空，宁可返回 507/422 报错并保留文件，
   也绝不静默产出 0 字节的"成功"。假成功是 RAG 系统最危险的 bug。
3. **回答必须可溯源** —— 每个 chunk 保留 `doc_id + 页码`，回答附引用列表，
   员工能翻回原文第 N 页核对。不信任不可溯源的答案。
4. **位置即语义（2026-09-20 新增）** —— 图文混排文档里，图片的识别内容必须插在
   原文出现的位置。"如图1所示"与图内容被切散 = 检索会引用看不见的图。
   丢弃图片信息（流程图/架构图/盖章页）按严重 bug 对待，不按功能缺失对待。

                        │        pypdfium2渲染→qwen3.5-ocr     │
                        │        保留[页码 N] 连续3页失败熔断     │
                        │        │                             │
                        │  L3 统一中间格式 ParsedDoc            │
                        │   {text, metadata{parse_method,      │
                        │    pages, route}}                    │

   员工提问                ┌─────────────────────────────────────┐
  ──────────────────►     │           问答链路                    │
   "立项流程是什么?"        │  embedder(查询向量化)                  │

## 四、接入层 4 层框架详解（v2 改造的核心）

> 改造前：`parser.py` 只按扩展名分发，扫描版 PDF 抽出 0 字**静默入库**，
> 无任何检测、去重、门禁 —— 这是当时教材进不了库的根因。

### L1 格式路由（`app/services/router.py`）

- 按扩展名初分类 → 对 PDF 额外做**零成本抽样试提取**：抽前 6 页文字层，
  若字符量 ≈0 判定为扫描版。
- 输出 `RouteDecision`：7 条路（direct_pdf / scanned_pdf / docx / text / tabular / image / unsupported）。
- 成本：零（pypdf 本地抽文字，不调任何模型）。

### L2 分级解析（`app/services/parser.py` + `ocr_parser.py`）

按路由分流，成本从低到高：

| 路径 | 方式 | 成本 |
|---|---|---|
| 原生 PDF / 文本 | pypdf 直读 | ¥0 |
| Word (.docx) 纯文字 | python-docx 按 body 原始顺序直读(段落/表格交错保序) | ¥0 |
| Word (.docx) 含内嵌图片 | 直读 + **图片 OCR 分流(D6)**:run 中检测 `a:blip r:embed` → 取 image part bytes → 留档 `data/media/{doc_id}/imgN.{ext}` → qwen3.5-ocr 双轮识别(先抠文字,<10 字则转述流程图/架构图节点关系)→ 原位插 `[图片N]` + `[图片N内容: ...]` | 约 ¥0.01-0.05/张 |
| 扫描版 PDF / 图片 | pypdfium2 逐页渲染 JPEG → qwen3.5-ocr | 约 ¥1-3/本书 |
| （兜底未启用） | 多模态大模型 | 更贵，暂不需要 |

D6 docx 图片 OCR 细则（2026-09-20 上线，修复"内嵌图片被整体丢弃"严重 bug）：
- **位置即语义（公理四）**：识别内容插在原文出现的位置，chunker 有原子保护——
  `[图片N内容:...]` 与其前 200 字上下文强制同 chunk，含标记的句子不切断；
- 成本护栏：单 docx 图片 OCR 上限 `settings.docx_ocr_max_images`（默认 30 张），
  超出只留 `[图片N]` 占位，metadata 记 `skipped_images`；
- 无文字且描述失败的图 → `[图片N: 装饰图片]` 占位；
- 额度错误与 PDF 扫描路径同语义：`OcrQuotaError` → 任务 failed + 原因，文件保留；
- docx 图片 OCR 与扫描 PDF/图片上传共用一把全局串行锁（`OCR_LOCK`），防并发限流；
- .doc（老格式）不在支持范围，维持现状（扩展名 400 拒绝）。

OCR 关键设计：
- 每页文本前缀 `[页码 N]`，为"可溯源"保住页码；
- **连续 3 页失败即熔断**，不烧完 600 页才报错；
- 403 额度类错误 → 抛 `OcrQuotaError`，接口回 **507**，文件保留可重传。

### L3 统一中间格式（`ParsedDoc`）

不管哪条路解析出来，都归一成同一结构：
```python
ParsedDoc(text=..., metadata={"parse_method": "ocr:qwen3.5-ocr",
                              "pages": 618, "route": "scanned_pdf", ...})
```
下游 chunker/embedder 不需要知道文件原来是什么格式。

### L4 质量门禁（`app/services/gate.py`）

| 检查 | 时机 | 拦截标准 | 响应 |
|---|---|---|---|
| 哈希去重 | 解析**前** | sha256 已在注册表 | 409（省一次解析费） |
| 空/过短 | 解析**后** | 文本 < 300 字 | 422，不入库 |
| 乱码率 | 解析**后** | 非正常字符占比过高 | 422，不入库 |

## 五、问答链路详解

1. 查询 → `embedder.embed_query()` 向量化（百炼 API）
2. Qdrant dense 召回 top20
3. `reranker`（qwen3.7-text-rerank）精排取 top5；rerank 失败自动回退 dense 顺序
4. `build_rag_prompt()`：系统提示 + top5 chunks（带来源标注）+ 用户问题
5. `llm.achat()` → qwen3.8-flash 生成（支持普通 `/api/chat` 和流式 `/api/chat/stream`）
6. 响应附 `citations`：每条含 doc_id、source 文件名、**页码**、score、原文片段
7. 对话存 `app/data/history/`，`/api/history/*` 可查

## 六、使用方式

### 6.1 启动 / 停止

```bash
cd enterprise-rag-kb
# Qdrant（Docker，通常常驻）
docker ps | grep qdrant || docker start <qdrant容器>
# 后端
./venv/bin/python -m uvicorn app.main:app --host 0.0.0.0 --port 9012
# 健康检查
curl http://127.0.0.1:9012/health
```

### 6.2 上传文档（管理员）— D4 异步化（2026-09-20 起）

```bash
curl -F "file=@制度手册.pdf" http://127.0.0.1:9012/api/upload
```
上传接口**立即返回**（流式落盘 + L1 路由 + L4 哈希去重后即回，不等解析）：
```json
{"doc_id":"1e1cc9f2","filename":"布丁扫描2026-08-07.pdf","size":5260029,
 "route":"scanned_pdf","status":"queued"}
```
解析/OCR/切块/入库由后台线程池异步执行（threading + queue，未引入 Celery/Redis）。

**状态机**：`queued → parsing（带 ocr_progress: done/total 页）→ ingested / failed(reason)`，
持久化在 `app/data/upload_tasks.json`，服务重启不丢已完成记录
（重启瞬间未完成任务被如实标记 failed="服务重启导致任务中断"，文件保留可重传）。

**状态查询**：
```bash
curl http://127.0.0.1:9012/api/upload/status/{doc_id}
# {"status":"parsing","ocr_progress":{"done":6,"total":14},...}
curl http://127.0.0.1:9012/api/upload/list
# {"documents":[已入库 source 列表],"tasks":[全部任务状态]}
```
**OCR 类任务全局串行**（scanned_pdf / image / 含图 docx 共用一把锁），
防并发打 DashScope 限流；普通解析/embedding 不受限（2 个工作线程并行）。

**前端进度**：内置页上传区自动轮询 status 接口，显示
⏳排队中 → 解析中 N/M 页（进度条按页推进）→ ✓已入库(N块) / ✗失败:原因，无前端框架。

- 支持：pdf / docx / txt / md / png / jpg 等（路由全集见 `router.py`）
- 单文件上限 **500MB**（`settings.max_file_size`，流式分块写盘边写边计数，
  超限中止并删半成品，不占内存——实测 550MB 上传进程峰值 RSS ~171MB）
- 同步语义保留：扩展名不支持/空文件 → 400；重传同文件 → 409；
  异步阶段语义：空/短/乱码 → failed+门禁原因；OcrQuotaError → failed+原因且**文件保留**
- 已入库清单：`GET /api/upload/list`

### 6.3 提问（员工）

```bash
curl -X POST http://127.0.0.1:9012/api/chat \
  -H "Content-Type: application/json" \
  -d '{"question":"项目立项要走什么流程？","session_id":"demo"}'
```
回答 JSON 中的 `citations[]` 即引用出处（文件名+页码+原文片段）。
前端简单对话页：浏览器打开 `http://<服务器IP>:9012/`。
流式输出用 `/api/chat/stream`（SSE）。

### 6.4 校对已入库内容

对 OCR 结果不放心的页，可在问答时通过 citations 跳回原文核对；
发现严重识别问题 → 删除该 doc 重新上传（哈希注册表同步删）。
